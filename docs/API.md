# AgentFleet API reference

The orchestrator exposes a REST API and a WebSocket event bus. The React admin
console, the Flutter companion app and the Python SDK all speak to it.

Base URL: `http://<host>:8080` by default (`API_PORT` in `.env`).

This document is generated by reading `backend/internal/httpapi/server.go`, which
is the single place every route is registered. If a route is not listed here, it
is not registered. The counts: 138 patterns, of which 131 are behind
authentication and 7 are not.

---

## Authentication and authorisation

A JWT bearer token, from `POST /api/auth/login`:

```http
Authorization: Bearer <token>
```

Or a long-lived **API key**, in the same header, for a script or a CI job that
should not be holding somebody's password:

```http
Authorization: Bearer af_<id>_<secret>
```

A key is issued from the admin panel or `POST /api/api-keys`, and the secret is
shown once — only a hash of it is stored, so there is no way to read it back.
A key acts with its owner's role, which means every check below behaves
identically whether a person or a script made the call. Revoking the key, or
disabling the person it belongs to, stops it immediately.

Two endpoints also accept `?token=<jwt>` in the query string, because a browser
WebSocket and an embedded VNC frame cannot set a header: `/api/events` and
`/vnc/{id}/`.

### Roles

Three ranked roles. Each route below is marked with the minimum it requires.

| Role | Rank | Can |
| :--- | :--- | :--- |
| `auditor` | 1 | Read. Telemetry, task audit logs, view-only desktop streams. |
| `operator` | 2 | Everything an auditor can, plus instance lifecycle, tasks, skills, chat, takeover. |
| `admin` | 3 | Everything, plus users, provider credentials, the secret vault, webhooks and cron triggers. |

`any` in the tables below means any authenticated user, auditor included.

### Organisations, departments and per-bot grants

Layered on top of the three roles, and evaluated inside the handlers rather than
at the route. An organisation (a department) has members with an org role, and a
bot can carry per-bot permission grants. `GET /api/me/permissions` is the
endpoint a client should use to decide what to show — it returns the caller's
effective permissions rather than making the client re-derive them.

This is why the `/api/orgs` routes are gated at `operator` and not `admin`: the
real authorisation happens per organisation inside the handler, and gating the
route at admin would stop an org's own operator administering it.

## 1. Unauthenticated endpoints

These seven carry no `Authorization` requirement. Five of them authenticate by
some other means; know which is which.

| Method | Path | Notes |
| :--- | :--- | :--- |
| `GET` | `/healthz` | Genuinely public liveness check. |
| `POST` | `/api/auth/login` | Genuinely public. |
| `POST` | `/api/auth/bootstrap` | Creates the first administrator. Refused once any user exists. |
| `POST` | `/api/webhooks/{token}` | The token in the path is the credential. Body is capped at 1 MiB. |
| `GET` | `/api/providers/oauth/callback` | Where providers redirect back to. Authorised by the single-use `state` value, not by a session. |
| `GET` | `/api/events` | Not route-gated, but the handler parses the token from `?token=` and returns 401 without one. |
| `ANY` | `/vnc/{id}/` | Same: authenticates from `?token=`, then sets a cookie scoped to `/vnc/{id}/` so noVNC's own relative asset requests are carried. Prefix match, no method restriction. |

### `POST /api/auth/bootstrap`
Creates the initial administrator. Available only while the database has no users.
- Request: `{"email": "admin@example.com", "password": "secure-password"}`
- Response `201`: `{"user": User, "token": "jwt..."}`

### `POST /api/auth/login`
- Request: `{"email": "operator@example.com", "password": "password"}`
- Response `200`: `{"user": User, "token": "jwt..."}`

### `POST /api/instances`
```json
{
  "name": "build-sandbox-1",
  "tier": "developer-heavy",
  "shell_access": true,
  "sudo_access": false,
  "egress": {
    "allow": ["github.com", "registry.npmjs.org"],
    "block_local": true
  },
  "override": { "memory_mb": 16384, "vcpu": 8 }
}
```
Response `201`: an `Instance`.

Note that `sudo_access` is applied after the container is running, by clearing or
setting the setuid bit on `/usr/bin/sudo`, and can be changed later through
`PUT /api/instances/{id}/access`. See [SECURITY.md](SECURITY.md) for what that
does and does not guarantee.

### `POST /api/instances/{id}/act`
Manual takeover. `shell`, `python`, `mount_tool` and `call_tool` are refused with
`403` when the instance has shell access disabled — the same gate the agent loop
applies, deliberately duplicated so takeover cannot be used to route around it.

## 6. Model providers and connections

| Method | Path | Role | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/providers` | admin | List configured connections. Secrets are never returned. |
| `POST` | `/api/providers` | admin | Create a connection. |
| `PUT` | `/api/providers/{id}` | admin | Update a connection. |
| `DELETE` | `/api/providers/{id}` | admin | Delete a connection. |
| `POST` | `/api/providers/reorder` | admin | Reorder the global fallback chain. |
| `POST` | `/api/providers/{id}/probe` | admin | Health-check a connection. |
| `GET` | `/api/providers/models` | admin | Ask a provider what models it actually serves. |
| `GET` | `/api/providers/ollama/models` | admin | Legacy, kept for compatibility. |
| `GET` | `/api/providers/antigravity/models` | admin | Legacy, kept for compatibility. |

Everything in this section is admin-only, including reading. Listing was open
to any signed-in user, and the mutating model-combination and per-bot chain
routes needed only operator — so someone handed a single bot to drive could
read every provider's base URL and OAuth client id, and rewrite the chain the
whole fleet falls back through. None of that belongs to an operator who was
given a machine to use. A test over the route table keeps it that way.

`GET /api/providers/models` is additionally sensitive because an API key can
arrive on it as a query parameter, for probing a connection that has not been
saved yet.

Provider kinds: `openai`, `anthropic`, `gemini`, `antigravity`, `ollama`,
`openai-compatible`.

### Signing in instead of pasting a key

| Method | Path | Role | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/providers/oauth/redirect` | admin | Returns the exact redirect URI to register with the provider. |
| `POST` | `/api/providers/{id}/signin/url` | admin | Starts an authorization-code + PKCE flow; returns the consent URL to open. |
| `GET` | `/api/providers/signin/status` | admin | Poll the outcome of a flow in progress. |
| `GET` | `/api/providers/oauth/callback` | public | Where the provider redirects. Authorised by `state`. |
| `POST` | `/api/providers/{id}/signin` | admin | Start a device-style sign-in. |
| `GET` | `/api/providers/{id}/signin` | admin | Its status. |
| `DELETE` | `/api/providers/{id}/signin` | admin | Sign out and discard the stored credential. |

The app opens the provider's own consent page and polls for the outcome; the
exchange happens on the server, so the app never holds a client secret, an
authorization code or a token.

`GET /api/providers/oauth/redirect` exists because a redirect URI has to match
what the server sends character for character, and having two places derive it
independently is the most common way an OAuth setup fails.

A signed-in provider stores its credential under a different vault ref from its
API key, so switching a connection between the two does not destroy the one it is
not currently using.

## 7. Model combinations and per-bot chains

A **combination** maps roles to providers — "these eyes, that brain". A bot's
chain is an ordered list whose entries are each either a provider ID or a
combination ID. Roles are `vision`, `reasoning`, `chat`, `summarize`, `refine`.

| Method | Path | Role | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/model-combos` | admin | List combinations. |
| `POST` | `/api/model-combos` | admin | Create one. |
| `PUT` | `/api/model-combos/{id}` | admin | Update one. |
| `DELETE` | `/api/model-combos/{id}` | admin | Delete one. Bots referencing it keep working; the entry is dropped when the chain is expanded. |
| `PUT` | `/api/instances/{id}/models` | admin | Set a bot's chain. Entries may be provider IDs, combination IDs, or a mix. |
| `GET` | `/api/instances/{id}/models/resolved` | admin | Show which model would actually serve each role for this bot, after expansion and fallback. |

`GET /api/instances/{id}/models/resolved` is the endpoint to reach for when a bot
is not using the model you thought it was. It answers per role.

## 11. Pipelines

Multi-bot DAG workflows. The engine runs nodes **one at a time, in topological
order**. It does not run independent nodes in parallel, and it does not evaluate
edge conditions — the `condition` field on an edge is stored and returned but
nothing acts on it. The only branching is that an error aborts the run.

| Method | Path | Role | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/pipelines` | any | List pipelines. |
| `POST` | `/api/pipelines` | operator | Create or replace. |
| `GET` | `/api/pipelines/{id}` | any | One pipeline. |
| `DELETE` | `/api/pipelines/{id}` | admin | Delete. |
| `POST` | `/api/pipelines/{id}/run` | operator | Start a run. |
| `GET` | `/api/pipelines/{id}/runs` | any | Run history. |

Note the asymmetry: saving and running a pipeline needs `operator`, deleting one
needs `admin`.

## 16b. Shared work catalog

Where the agents put the work itself. Before this they could message each other
and share credentials but nothing else, so whatever one produced lived in its
container and died with it.

An item's `kind` decides what the app does with it, not how it is stored:

- `file` — text. Notes, code, data. Shown as text.
- `app` — one self-contained HTML document, rendered and run in a web view.
  It must actually be a web page and must not load anything over the network:
  the view has no network, so an external script would never arrive. Both are
  refused at publish time with a message saying what is wrong.
- `workspace` — groups related items so several agents can work on one thing.

Items are scoped like secrets: filed to a department, visible to that
department; unfiled, admin-only. Publishing a name that already exists in the
same workspace is an edit that bumps `version`, so improving a colleague's work
is not a second copy nobody notices.

| Method | Path | Role | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/work` | any | The catalog, filtered to what you may see. |
| `GET` | `/api/work/{id}` | any | One item. 404 if you may not see it. |
| `POST` | `/api/work` | operator | Publish or replace an item. |
| `DELETE` | `/api/work/{id}` | operator | Remove one. A workspace takes its contents. |

Publishing is also what moves a shared job along: when an agent working on a
fleet request publishes, whoever has the next part is woken and handed it. See
the fleet-comms section for how parts are assigned.

Agents reach the same catalog through two actions rather than HTTP:
`publish_work` (with `work_name`, `work_kind`, `work_workspace` and the content
in `text`) and `read_work` (with `work_name`). Both are keyed by name, because
agents refer to each other's work by what it is called.

## 25. Desktop stream

`/vnc/{id}/` reverse-proxies the sandbox's noVNC. Authenticate with `?token=`;
the handler then sets a cookie scoped to that path so noVNC's own relative asset
requests carry credentials. Auditors are routed to the container's second,
`-viewonly` VNC server rather than being asked not to interact — read-only
enforced in the client would not survive an edited URL.

## 26. WebSocket events

```
ws://localhost:8080/api/events?token=<jwt>
```

Payload:

```json
{
  "type": "task.step",
  "instance_id": "inst-123",
  "task_id": "task-456",
  "payload": { "step": 4, "action": { "action": "click", "target": "Submit" } },
  "at": "2026-08-28T19:50:00Z"
}
```

The topics emitted by the backend, in full:

| Topic | Emitted when |
| :--- | :--- |
| `task.state` | A task changes state: `running`, `awaiting_human`, `succeeded`, `failed`, `cancelled`. |
| `task.step` | A turn completes. |
| `task.spawned` | An agent spawns a child. |
| `agent.step` | A step within the agent loop. |
| `instance.state` | An instance changes lifecycle state. |
| `instance.deleted` | An instance is destroyed. |
| `alert` | An agent is blocked and needs a human. |
| `alert.resolved` | The operator answered. |
| `chat` | A chat message. |
| `manual.act` | An operator sent an action through takeover. |
| `record.started` / `record.stopped` | A demonstration recording began or ended. |
| `skill.refined` | A skill was refined from a trace. |
